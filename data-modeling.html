Module 2 — Data Modeling

Build a clean semantic model with a deliberate grain, predictable filter propagation, reusable dates, suitable calculated objects and efficient storage.

Concept 1

Star schema, fact/dimension design & grain

  • Fact tables store measurable events at a defined grain; dimensions store descriptive attributes used to group/filter.
  • Prefer a star schema with dimensions on the one side and facts on the many side.
  • State grain in plain language before modeling.
  • Do not aggregate away detail needed for transaction counts, distinct customers or later slicing.
  • Bridge tables can represent genuine many-to-many entity relationships.
Exam gotcha: A DAX measure aggregates at query time. Power Query Group By changes the physically stored grain.
Concept 2

Cardinality, cross-filter direction & filter propagation

  • One-to-many is the normal dimension-to-fact cardinality; the one-side key must be unique.
  • Use single-direction dimension → fact filtering by default.
  • Bidirectional filtering can be valid but may create ambiguity and performance complexity.
  • In a standard star, a filter on one dimension does not automatically flow backward through the fact to another dimension.
  • Column cardinality means number of distinct values; it is not relationship cardinality.
Exam gotcha: Do not turn on bidirectional filtering merely to make slicers reduce one another unless the business requirement justifies it.
Concept 3

Date tables, active/inactive relationships & role-playing dimensions

  • A Date table should have one row per date, unique/nonblank dates and the needed continuous range.
  • Sort Month Name by Month Number; sort Month-Year by a sequential YearMonth key.
  • Only one of multiple relationships between the same two tables can be active at a time.
  • USERELATIONSHIP() uses an inactive relationship for a calculation.
  • Use separate role-playing Date dimensions when users need independent simultaneous Order Date and Ship Date slicers.
DAX
Shipped Sales =
CALCULATE (
    [Total Sales],
    USERELATIONSHIP ( 'Date'[Date], Sales[ShipDate] )
)
  • CALCULATE reevaluates [Total Sales] under modified relationship context.
  • USERELATIONSHIP activates the existing inactive ShipDate relationship for this calculation.
  • The model's active OrderDate relationship is not permanently changed.
Exam gotcha: USERELATIONSHIP solves a calculation-by-alternate-date problem; it does not make one Date table behave like two independent slicers.
Concept 4

Measures, calculated columns, calculated tables & quick measures

  • Measures are dynamic scalar calculations evaluated in filter context.
  • Calculated columns produce row-level stored values available for grouping/slicing.
  • Calculated tables are DAX-created model tables evaluated during processing/refresh.
  • Prefer source/Power Query for static shaping when practical; use measures for dynamic analysis.
  • Quick measures generate DAX for supported common calculations—understand the generated logic.
Exam gotcha: A measure is not a stored categorical column and therefore is not normally a slicer field.
Concept 5

Model properties & performance optimization

  • Remove unused rows/columns, especially high-cardinality long text.
  • Reduce unnecessary granularity and precision when requirements allow.
  • Set useful names, formats, data categories and default summarization.
  • Numeric identifiers often should use Don't summarize; postal/geographic fields should use appropriate data categories.
  • Performance Analyzer identifies slow report visuals; DAX query view lets you author/run DAX queries against the model.
Exam gotcha: Hiding a column improves the field list but does not reduce VertiPaq storage and is not security.
